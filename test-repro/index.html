Make the Revision Delta tell the truth

The critique stage reviews each draft version in isolation, and the system then guesses which findings are “the same” as last time. On an unchanged draft that guess is wrong about half the time — and the wrong number is the one a client reads.

surface Proposal Review · Revision Delta stage draft_critique model claude-opus-4-8 status awaiting approval repo main ff88ba1

01Goal

When a v2 draft is reviewed, the Revision Delta reports how many prior findings were resolved, how many are persisting, and how many are newlyIntroduced. Today those numbers are inferred after the fact by fuzzy-matching two independently-generated finding sets. Because the model restructures its output between runs — merging two findings into one, surfacing a genuinely different item — the inference is wrong even when nothing about the draft changed.

This spec makes the model assert the diff instead: v2’s critique receives v1’s findings and states, per finding, which prior issue it continues and which prior issues it judges fixed. The existing matcher is kept as a fallback and as a disagreement detector, not deleted.

Acceptance criteria — all checkable

  1. The identical-artifact regression test passes. Re-running the pipeline with a v2 whose artifact bytes are identical to v1 yields resolved = 0 and newlyIntroduced = 0 for the solicitation lens. Measured baseline today: 8 of ~16 persisting, the rest split across resolved and newly-introduced.
  2. A real edit still moves the numbers. A v2 that genuinely fixes one finding reports that finding as resolved and does not mark it persisting — i.e. the fix does not simply pin everything to “persisting”.
  3. Deterministic lenses are untouched. file and package findings continue to match exactly by findingKey; their counts are byte-identical before and after this change.
  4. Disagreement is recorded, not hidden. Where the model’s assertion and the fuzzy matcher disagree, the run records it in a countable field so the two methods can be compared over time.
  5. npm test and npx tsc --noEmit clean, with new unit tests covering the assertion parser and the fallback path.

02What’s actually wrong

Read from the code, not from the ticket

pipeline.ts:235  critiqueDraft({ alignedBlock, gapsBlock, lmBlock })  ← no prior version in scope
pipeline.ts:305  if (draft.supersedesDraftId) { … }  ← prior loaded 70 lines LATER
pipeline.ts:325  matchVersions(prior, current)  ← the diff is inferred here

The critique is generated with no knowledge that a previous review exists. The prior version is fetched afterwards purely so versioning.ts can pair up the two sets — exact findingKey first, then a Jaccard-similarity fuzzy tier anchored on the aligned L/M item.

The matcher is not the bug, and this spec does not change it. Your own measurement: all deterministic findings matched exactly, and the fuzzy tier lifted persisting from 5 to 8 of ~16. The residual is generation variance — two different-but-both-valid descriptions of the same issue. Forcing those to match would be a false positive, which is why no threshold change fixes it.

The lever from the backlog that is now dead: “pin temperature: 0 on draft_critique.” That stage routes to claude-opus-4-8, where the parameter is rejected. There is no sampling-determinism knob available on this path, which is precisely why the fix has to be structural.

03Blocking questions

1. When the model’s assertion and the fuzzy matcher disagree, which wins?

The model may claim a finding continues prior finding X while the matcher pairs it with Y — or claim a prior finding is resolved while the matcher finds a strong textual match still present.

Recommended: the model wins for the solicitation lens, and the disagreement is counted. It is the only party with the semantic context to know that “Key Personnel title inconsistent” and “QCP named inconsistently” were merged into one finding. The matcher stays authoritative for file and package, which are deterministic and already correct. Recording the disagreement rate is what lets us find out if that call was right.

2. Should an unchanged artifact skip re-critique entirely?

The pipeline already carries lens-1 findings forward when an artifact’s hashText is unchanged. The same short-circuit could apply to the critique — making the identical-artifact case correct by construction rather than by better prompting.

Recommended: no — keep re-critiquing, and use the identical-artifact case only as the regression test. Short-circuiting would make criterion 1 pass trivially while leaving the real case — a draft where two of twelve sections changed — just as wrong. It would also mean a v2 never benefits from an improved prompt or model. Worth doing later as a pure cost optimisation; it is not a fix.

04Assumptions

  1. ~16 findings per review is the working scale, so appending v1’s findings to the v2 prompt adds roughly 2–4k tokens against a 20k output budget. Falsified if a large package produces 60+ findings, at which point the prior block needs truncating by severity.
  2. The instability is confined to the solicitation lens. Stated in the backlog and consistent with the code: file and package findings are produced by deterministic lint, not by the model.
  3. A prior finding’s id is safe to expose to the model. It is an opaque UUID; the prompt already carries the draft text, which is the sensitive material. Falsified if ids ever encode client-identifying information.
  4. The operator’s disposition data must survive. carriedFromFindingId drives disposition inheritance and the incorporation_failure signal, so the asserted link must populate the same field the matcher does — not a parallel one.
  5. Out of scope: changing the matcher’s fuzzy tier, changing severity or category taxonomy, the native-XLSX export, and the segmentation excerpt-quality item. Also out of scope: benchmarking which model should run this stage — that is deliberately deferred until deliverable volume justifies it.
  6. No backfill. Existing reviews keep their inferred deltas. Falsified if you want the 3 historical deliverables recomputed, which would need a migration.

05Plan

#Change→ verify
1 Move the prior-version load above the critique call. pipeline.ts: fetch prior solicitation-lens findings before line 235 and pass them into CritiqueInput as a new optional priorFindings. v1 path unchanged (no prior → field absent); existing tests pass
2 Extend the critique tool schema in stages.ts: each finding gains continues_prior_id (nullable), and the top level gains resolved_prior_ids: string[] — the prior findings the model judges fixed. schema round-trips; zod parse rejects an id not in the supplied prior set
3 Render the prior block into the prompt — id, title, severity, section_ref per prior finding, with an instruction to cite continues_prior_id when re-raising the same issue and to list a prior id in resolved_prior_ids only when the draft now satisfies it. prompt snapshot test; no draft text duplicated into the block
4 Consume the assertion in the carry-forward, replacing the matcher's result for the solicitation lens only. Assertion → carriedFromFindingId; matcher still runs, and its result is compared. unit test: asserted link populates the same field the matcher would; disposition inheritance intact
5 Record disagreement. Persist a per-run count of (asserted ≠ matched) and (asserted-null, matcher-found) so the two methods are comparable over time. the count is queryable and non-null on a v2 run
6 Fallback path. If the model omits the fields entirely (or cites unknown ids), fall back to the matcher for that finding and count it. unit test with a stubbed critique that omits the fields → behaviour identical to today
7 The regression test. A fixture v2 with a byte-identical artifact, asserting resolved = 0 and newlyIntroduced = 0. fails against today’s code (baseline 8/16), passes after

Rejected alternatives

  • Loosen the fuzzy matcher’s threshold — rejected: your own measurement says the residual mismatches are genuinely different descriptions, so forcing them to pair produces false positives. It trades one wrong number for another.
  • Pin temperature: 0 — rejected: not available on claude-opus-4-8. This is the backlog’s lever (b) and it is stale.
  • Replace the matcher entirely with the model’s assertion — rejected: it would discard the exact-findingKey tier that makes deterministic lenses correct today, to fix a problem those lenses do not have.
  • A second “diff” model call comparing the two finding sets — rejected: it adds a stage and a cost, and re-introduces the same variance one layer up. The critique already has both sides in context; asking it once is cheaper and more grounded.

06Risk

The honest one: asking a model to say “this is the same issue as before” may bias it toward re-raising prior findings it would not otherwise have surfaced — trading false resolved for false persisting. Acceptance criterion 2 exists specifically to catch that, and criterion 4’s disagreement count is the ongoing monitor. If it materialises, the mitigation is to withhold prior titles and supply only ids plus section refs, so the model must re-derive the issue before it can claim continuity.

Scope note: this touches a client-facing deliverable’s numbers, so per the standing rule it gets an adversarial audit before commit — with particular attention to the disposition-inheritance path, where a wrong link silently mislabels an operator’s accepted fix as an incorporation_failure.
